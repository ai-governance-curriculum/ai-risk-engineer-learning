# Lab 02 — Provenance Package Authoring Drill (Data Card YAML + Model Card + CycloneDX ML-BOM Skeleton)

**Duration:** 45 minutes · **Format:** guided practice, YAML / markdown / JSON authoring on a fixed fabricated LLM application

## Objective

Internalise the chapter-04 five-layer **provenance package** shape — data provenance (Datasheets / Data Cards), model provenance (Hugging Face-style Model Cards), component inventory (CycloneDX ML-BOM), cross-domain SBOM (SPDX 3.0 AI profile), build-integrity attestation (SLSA) — by authoring three of the five layers against a fixed fabricated running system (`HelpDesk`): a Data Card YAML for one corpus, a Model Card for the deployed fine-tune, and a CycloneDX ML-BOM skeleton enumerating the components. The lab drills the field shapes chapter 04 pins so that when **exercise 04** produces the real provenance package for your own deployed model, the engineering budget goes into the actual field content (dataset composition, upstream Model Card link, licence expression, hyperparameters, SLSA source references) rather than into inventing the schema.

The chapter-04 failure modes the shape forecloses: **"we can find it, give us a week"** (reconstruction, not provenance); **"it's a Hugging Face model"** (provenance stops at the base checkpoint); **"the dataset speaks for itself"** (no schema, no licence, no limitations note). The chapter's fix is explicit: provenance is "files with schemas that live alongside the artefacts they describe," regenerated on every release.

## Prerequisites

- Chapter 04 read — specifically "The provenance stack in one diagram (as prose)" (the five composing layers), "Layer 1 — Data provenance: Datasheets and Data Cards" (the ten field groups: identity, motivation and provenance, composition, collection, preprocessing / labelling, population coverage, uses, distribution and licence, maintenance, known limitations), "Layer 2 — Model provenance: Hugging Face-style Model Cards" (the nine provenance fields on the Model Card), "Layer 3 — ML-BOM with CycloneDX" (the seven ML components to enumerate for a deployed service and the CycloneDX 1.5/1.6 `component.type: machine-learning-model` and `type: data` shapes), and "Worked example — assembling the package for one model" (the folder layout and the `README.md` how-to-verify shape).
- Chapters 05 and 06 skimmed — the provenance package has reserved slots (`attestations/signature.sig`, `attestations/scan-report-{picklescan,modelscan}.json`) that exercises 05 and 06 populate; the lab leaves these as placeholders with an explicit "reserved for exercise 05/06" comment.
- A terminal where you can create a working directory and author YAML / markdown / JSON files. `python -c "import json; json.load(open('mlbom.cyclonedx.json'))"` or `jq . mlbom.cyclonedx.json` for a quick JSON-syntax check is enough; CycloneDX schema validation against the specification is out of scope for this lab (the real-tool wiring is exercise 04's job).
- No external access or compute required; the system brief, the corpus names, the Model Card metadata, and the component list are fixed below.

### Step 2 — Author the Data Card YAML (layer 1)

Chapter 04 §"Layer 1 — Data provenance" names ten field groups. Fill the Data Card for `helpdesk-transcripts-2024-2026-q3` — the fine-tune training corpus — into `datasets/helpdesk-transcripts-2024-2026-q3.datacard.yaml`. Use YAML so the file is both human-readable and machine-consumable by the downstream CycloneDX linkage in Step 5.

```yaml
# datasets/helpdesk-transcripts-2024-2026-q3.datacard.yaml
# Chapter 04 §"Layer 1 — Data provenance" ten-field-group schema

identity:
  name: helpdesk-transcripts-2024-2026-q3
  version: "2026-10-01"
  persistent_identifier: internal-dataset-registry://helpdesk/transcripts/2024-2026-q3@2026-10-01
  publication_date: 2026-10-01

motivation_and_provenance:
  why_created: Fine-tune the HelpDesk assistant on the company's own support-transcript distribution for improved answer faithfulness on billing + provisioning queries
  created_by: HelpDesk ML team
  funded_by: HelpDesk product org
  source_of_underlying_data: Internal ticketing system (billing + provisioning queues), extract pipeline `ticket-mining-v2.3`

composition:
  record_description: One record per customer-support ticket turn (user-utterance + agent-response pair); PII-redacted via Presidio before ingestion
  record_count: 148_320
  representation: JSONL; fields `turn_id`, `tenant_tier` (standard | enterprise), `queue` (billing | provisioning), `user_utterance_redacted`, `agent_response_redacted`, `escalation_flag`, `timestamp`

collection:
  how_collected: Mined from the production ticketing system between 2024-01-01 and 2026-09-30; the `ticket-mining-v2.3` extract pipeline runs on the warehouse replica, applies Presidio PII redaction, and writes JSONL to S3
  from_whom: Customers of the billing-and-provisioning product; agents are company employees
  over_what_period: 2024-01-01 to 2026-09-30 (33 months)
  under_what_consent: Internal consent per employment agreement (agents) + customer terms-of-service data-use clause v4.2 (customers)

preprocessing_and_labelling:
  transformations:
    - Presidio PII redaction (names, account numbers, phone, email, SSN-shaped tokens)
    - normalisation of ticket-system artefacts (ticket-id tokens, markdown stripping)
    - de-duplication of exact-match response pairs
  labelled_by: n/a (self-labelled — the agent response is the training target); no human re-adjudication at ingestion
  label_schema: Target is the redacted agent response; `escalation_flag` is the binary auxiliary label from the ticketing system

population_coverage:
  represented:
    tenant_tier:
      standard: 68.2% of records
      enterprise: 31.8% of records
    queue:
      billing: 54.1%
      provisioning: 45.9%
    language: English only
  not_represented:
    - non-English customers
    - the `enterprise-plus` tier launched 2026-10 (post-cutoff)
    - product lines outside billing-and-provisioning
  known_distributional_biases:
    - agent-response style skewed toward the US support-team norms (two of three support regions)
    - under-representation of refund-dispute edge cases (only 2.4% of records; see refusal-fixtures corpus for compensating coverage)

uses:
  intended_uses:
    - fine-tuning `helpdesk-finetune` v1.3.x
    - evaluation of faithfulness and coverage on billing + provisioning queries
  unsafe_or_misleading_uses:
    - inference outside the billing-and-provisioning domain
    - any model intended for non-English populations
    - any clinical, legal, or financial-advice context
  downstream_tasks_tested:
    - closed-domain Q/A on billing + provisioning
    - escalation recommendation (binary)

distribution_and_licence:
  distribution: Internal only; S3 bucket `internal-datasets/helpdesk-transcripts` with read-only IAM role scoped to the fine-tune training job
  licence: Internal; no external redistribution; see `helpdesk-transcripts-2024-2026-q3.license.txt`
  access_controls: IAM role `role/helpdesk-training-r`; read audit via CloudTrail

maintenance:
  current_owner: HelpDesk data-platform peer (contact `data-platform@internal`)
  update_cadence: Quarterly snapshots; monotonic version strings keyed to snapshot date
  sunset_policy: Snapshots retained for 36 months per data-retention policy; superseded snapshots marked `superseded-by: <newer-snapshot>` in the registry

known_limitations:
  - "English-only; downstream use on non-English traffic is out-of-scope (see uses.unsafe_or_misleading_uses)"
  - "Enterprise-plus tier launched 2026-10 is not represented; retrain on the 2026-Q4 snapshot before HelpDesk v1.4.0"
  - "Agent-response style skews toward US-support norms; see fairness evaluation on `tenant_tier` and the mod-106 report for the measured per-slice delta"

cross_references:
  mod_102_harm_rows: [HM-HD-04, HM-HD-12]
  mod_103_register_rows: [HR-CS-FAIR-08, HR-CS-PROV-12]
```

## Checkpoint questions (self-check)

1. The Data Card lists `enterprise-plus` as a known limitation (not represented) even though the lab brief does not require that limitation to be flagged. Why is a limitation like this load-bearing on the provenance package? (*Chapter 04 §"Layer 1 — Data provenance" names "known limitations: what the maintainers explicitly know the dataset does not represent well" as one of the ten field groups; the chapter is explicit that "corpora without a Data Card / Datasheet are un-audited data — they should not enter training or evaluation for any model that will be validated under MRM or FDA." A Data Card that omits known distributional limitations is not the same as a Data Card that affirmatively says "this is known to be representative" — the omission creates the "the dataset speaks for itself" failure mode from the chapter's motivation. The `enterprise-plus` row is the Data Card doing its job: it carries the information downstream into the Model Card's `## Known limitations and out-of-scope uses` and into the register as an input to the drift / fairness monitors, so that when a 2026-Q4 report shows enterprise-plus traffic entering production, the data-coverage gap is a known pre-condition, not a surprise.*)

2. The Model Card's `## Safety and ethical considerations` cross-references mod-102 harm-row ids *and* mod-103 register-row ids — not only one or the other. Why both? (*Chapter 04 §"Layer 2 — Model provenance" names "safety and ethical considerations: cross-reference to harm-model rows (mod-102) and register rows (mod-103)" as a Model Card provenance field. The two cross-references answer two different auditor questions: mod-102 harm-row ids answer *which failure modes the design intended to resist* (conceptual-soundness evidence per chapter 01's second pillar); mod-103 register-row ids answer *which risks the system carries now, with what residual, and what evidence closes them* (the tiering-and-risk-rating heading of the MRM packet). A Model Card with only mod-102 ids is a statement of intent without carrying the residual-state evidence forward; a Model Card with only mod-103 ids skips the conceptual-soundness link. Both are required for the Model Card to function as provenance evidence under the chapter-01 MRM packet.*)

3. The ML-BOM lists `FoundationCo-LLM-3.5` as a component with `supplier: FoundationCo` and `licenses: FoundationCo API Terms v2.3`, but no weights hash. Why is this the correct shape, and what gets filled in exercise 02 that the ML-BOM references? (*Chapter 04 §"Layer 3 — ML-BOM with CycloneDX" names "Every third-party model API (bounded description)" as one of the ML components a minimum-viable ML-BOM enumerates, with fields for "Vendor, model, version pinned to, terms." The vendor hosts the model and does not release weights, so a weights hash is not available — hashing a vendor-hosted artefact you cannot download is impossible. The correct shape is a `supplier` and a `licenses` entry that points at the vendor's terms. The ML-BOM entry's `externalReferences` points at the SR 23-4 vendor file at `../../../mrm-packet/.../11-third-party-components/FoundationCo-LLM-3.5/` — the vendor file (exercise 02) carries the planning tier, due-diligence questionnaire, contract clauses won/walked-away, own-signal monitor spec, and termination plan. The ML-BOM is the inventory; the vendor file is the audit depth; the two are linked by the ML-BOM's external-reference pointer.*)

4. The folder reserves `attestations/signature.sig` and `attestations/scan-report-{picklescan,modelscan}.json` as named-for-exercises-05-06 rather than omitting them. Why is the named-reservation discipline part of chapter 04's shape? (*Chapter 04 §"Worked example — assembling the package for one model" names the complete package folder layout — including `attestations/` with signature and scan-report files — because the folder is designed to be **the same shape** at every release. Chapter 05 §"What you sign, at minimum" and chapter 06 §"The ingestion-gate policy" compose with chapter 04's provenance package rather than being parallel artefacts; the gate checks look at files in this folder. If the layer 6/7 slots are omitted rather than reserved, the gate implementation has no stable path to check for, and exercises 05-06 end up doing folder-rework as well as signing/scanning. The chapter's rule — "regenerated on every release rather than assembled after the fact" — requires the shape to be stable across releases, which means the signing and scanning slots exist from the first release even when they are not yet populated.*)

## Why this lab matters

Exercise 04 asks you to author the full provenance package for one deployed model of your real running system — Data Cards for at least three corpora, a Model Card with all nine provenance fields, a syntactically valid CycloneDX 1.6 ML-BOM, a syntactically valid SPDX 3.0 record with AI + Dataset profiles, and a SLSA v1.0 provenance record. If the schema for any of those is new at exercise-04 authoring time, the budget blows on learning CycloneDX's component types, SPDX's relationship vocabulary, and the Datasheet question set — not on the engineering content that actually matters (which corpora you cite; which vendor dependency is disclosed; which licence-expression syntax you use; which SLSA source references you can honestly claim). This lab drills the three most load-bearing layers (data, model, ML-BOM) on a fixed fabricated system so that exercise 04's time goes into real content and the two placeholder layers (SPDX 3.0, SLSA) are the only authoring work that remains new. The folder shape it drills is also what exercise 05 signs (one `.sig` per file in the folder, keyed by hash) and what exercise 06 scans (model artefacts in the component list). Getting the shape right here cascades through the module's terminal artefact — the end-to-end ingestion gate.
