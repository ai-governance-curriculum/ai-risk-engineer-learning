# Labs for mod-110-model-risk-management-and-supply-chain (Model Risk Management (MRM) for ML/AI and AI Supply Chain)

Three 45-minute guided drills. Each builds one atomic output-shape authoring skill the exercises assume, on a fixed running system (`HelpDesk`, a customer-support RAG assistant for a mid-size B2B SaaS company; in-house fine-tune `helpdesk-finetune` v1.3.0 on the vendor-hosted base `FoundationCo-LLM-3.5` v3.5.2; safetensors weights; the same `HelpDesk` carried through the mod-109 labs). The sponsoring organisation is a US bank subsidiary, so SR 11-7 / OCC 2011-12 is the parent MRM shape, SR 23-4 governs the `FoundationCo-LLM-3.5` vendor file, and FDA GMLP / PCCP are explicitly not applicable (not a medical device) — the change-management stub points at the FI's model-change policy. The labs do not duplicate the module's exercises — the exercises run against the reader's own primary running system (MRM packet assembly from mods 102-109 outputs; SR 23-4 vendor file against a real third-party dependency; PCCP slice against a real adaptive or SaMD-shaped system; full provenance package with real Data Cards, ML-BOM, SPDX 3.0, SLSA; cosign + Rekor signing and OPA/Kyverno gate; ModelScan + picklescan with a sandboxed malicious pickle). The labs drill the output shapes those exercises rely on against the fixed `HelpDesk` system with fabricated-but-plausible identifiers and metadata.

- [`lab-01-mrm-packet-shape-authoring-drill.md`](lab-01-mrm-packet-shape-authoring-drill.md) — 45 minutes. Author the chapter-01 MRM packet `README.md` for `HelpDesk` v1.3.0 end-to-end: the packet summary (US-bank context; SR 11-7 applicable; FDA not applicable with justification; validator identity `L35-eval-eng-alex`), the four-pillar coverage table (independence as a practice evidenced by the validation-owned CI service account; conceptual soundness as mod-102 harm-row cross-reference; ongoing monitoring as the mod-109 signal contract in file; effective challenge as register rows the developer would not have volunteered — `HR-CS-VEND-11`, `HR-CS-PROV-12`), the twelve-heading heading-to-artefact map (every heading cites a file path *and* the upstream mod-10N artefact it consumes; reserved slots for exercises 02 / 04 / 05-06 are named by name not blank), the independent-validation memo disposition line (conditional approve on the Data-Cards-pending finding), the gap list (four rows, every row with owner / target date / register row carrying the risk), and open items (register-side back-link; `v1.0` close conditions). Chapter 01 skill feeding exercise 01's packet assembly.
- [`lab-02-provenance-package-authoring-drill.md`](lab-02-provenance-package-authoring-drill.md) — 45 minutes. Author three of the five chapter-04 provenance layers for `helpdesk-finetune` v1.3.0: the ten-field-group Data Card YAML for the fine-tune training corpus `helpdesk-transcripts-2024-2026-q3` (identity, motivation and provenance, composition, collection, preprocessing / labelling, population coverage, uses with specific unsafe-or-misleading cases, distribution and licence, maintenance, known limitations with the `enterprise-plus` tier not-represented row — plus the paired licence text file); the nine-provenance-field Model Card markdown (identity + weights hashes, base checkpoint identity with parent-page SHA captured, fine-tuning corpus references by persistent id, training procedure with hyperparameters / seeds / framework pins, aggregate and per-`tenant_tier` disaggregated results, intended use, known limitations and out-of-scope uses, safety and ethical considerations cross-referencing mod-102 harm rows *and* mod-103 register rows, version history); and the CycloneDX 1.6 ML-BOM skeleton JSON enumerating all seven components (deployed fine-tune + LoRA adapter + vendor-hosted base + embedding + Presidio PII safety composite + two datasets) with the service-to-component `dependencies` tree that reflects the fine-tune-derives-from-base and the fine-tune-trained-on-training-corpus derivation chains. Includes the SLSA v1.0 placeholder with builder / buildType / invocation / materials / metadata shape and the SPDX 3.0 profile-list placeholder (full authoring deferred to exercise 04); the signing and scanning slots are reserved by name for exercises 05-06. The `README.md` closes with the three-question verify-from-the-folder rubric answered against this folder's contents. Chapter 04 skill feeding exercise 04's full-package authoring.
- [`lab-03-ingestion-gate-policy-authoring-drill.md`](lab-03-ingestion-gate-policy-authoring-drill.md) — 45 minutes. Author the chapter 05-06 registry-ingestion-gate policy end-to-end: the identity allow-list with two pipeline identities (no expiry — training + validation keyless) and one time-bound human exception identity (expiry claim embedded in the identity string; mod-112 waiver change-log entry); the nine ordered checks (format allow-list → picklescan → ModelScan → cosign signature → Rekor entry → SLSA floor at `v1.0 Build L2` → ML-BOM + Data Cards → evaluations passed → validation-owner sign-off) with scanners **before** signatures per chapter 06's cheap-and-destructive-first ordering, each check carrying its diagnostic shape; the pass-run log with one line per check; the fail-run log where a `.pt` tamper and a modified ML-BOM produce four distinct failing checks (1 format, 2 picklescan, 4 cosign on two files, 5 rekor) with the first-failing check prominent in the summary; the five-step exception template (written request → mod-112 risk-council decision with time-bound end date → register update → mod-109 compensating-control monitor → expiry review) with the "no exception is permanent by default" rule explicit; and the five-branch runtime-failure playbook (chapter 05's three branches — signing pipeline changed; artefact modified; signing service outage with fail-closed and "do not disable the check" rule — plus chapter 06's two branches — scanner finding at ingestion; re-scan flip against updated scanner rules). Chapters 05-06 skill feeding exercise 05's cosign + Rekor wiring and exercise 06's ModelScan + picklescan wiring and malicious-artefact drill.

Run the labs in order — lab 02 references the register rows and the packet-reserved provenance slot that lab 01 names, and lab 03 references the provenance folder layout that lab 02 builds and the identity-allow-list rule that lab 01's packet governance names. Together the three drills carry the atomic output-shape authoring skills that exercises 01, 04, 05, and 06 depend on, so when the exercises run on the reader's own primary running system the time goes into engineering judgement — which register rows carry which gap, which vendor disclosures are actually missing, which scanner finding is a real block versus a false positive the threshold should tune — not into inventing the artefact format. The chapter-02 SR 23-4 and chapter-03 FDA GMLP / PCCP shapes are exercised through the quiz and through exercises 02 and 03 directly rather than through a dedicated lab, because the engineering judgement in both chapters is the *content* of the vendor file / PCCP slice against the reader's real dependency, not the file layout — and the lab-level forcing function is covered by lab 01's MRM packet (which reserves the SR 23-4 vendor-file slot) and by lab 03's gate policy (which operates independently of regulated-sector framing).
