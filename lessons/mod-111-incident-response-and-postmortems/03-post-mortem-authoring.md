# Post-Mortem Authoring for Three Audiences

An engineering post-mortem written in the classical shape — timeline, root cause, contributing factors, action items — serves the engineering team well and serves no one else. An AI incident post-mortem has to survive three audiences: the governance council (mod-112) that owns programme-level risk decisions, the regulator that will read the document verbatim under an Article 73 / SR 11-7 / MDR obligation (chapter 05), and the engineering team that has to fix the thing. This chapter defines the post-mortem shape that carries all three loads, the incident-into-register update, and the corrective-action-plan (CAP) that closes the loop.

## Motivation

Three failure modes for AI incident post-mortems in the field:

- **Engineering-only post-mortem.** The document reads as a Git commit annotation — helpful for the next on-call, unintelligible to the governance council, and unusable to a regulator. When the regulator asks for the incident file, engineering scrambles to author a second document weeks later. The two documents disagree on details; that disagreement becomes the finding.
- **PR post-mortem.** The document is written in the voice of an external statement — heavy on reassurance, light on cause. It survives publication but does not update the risk register and does not close a CAP. Six months later the same incident recurs.
- **The dashboard post-mortem.** The document is a set of graphs from monitoring. There is no narrative, no cause, no owner, and no action items with due dates. It cannot be audited.

The engineering discipline is to write *one document* that carries the load for all three audiences, with the audience-specific extracts derived from it. That discipline is this chapter's shape.

## The three audiences and what each needs

Each audience reads for a different question. Naming those questions up front lets you design the document rather than write it and hope.

| Audience | Reads to answer | Non-negotiable content they need |
|---|---|---|
| **Engineering team** | What broke, what to fix, what to add to CI | Timeline, causal chain, evidence pointers (traces, deltas), code / config / suite changes required, owners, due dates, fixture back-feed link (chapter 04) |
| **Governance council (mod-112)** | Does the risk register still tell the truth; does the programme's risk appetite still hold; are there programme-scale actions | Harm-model row referenced, register-row residual movement, appetite comparison, cross-system exposure, CAP owner + cadence, sign-off |
| **Regulator (or auditor)** | Is the obligation met — did the organisation detect, report on time, act on the correct information, and prevent recurrence | Facts of the incident and impact; regulatory classification (Article 73 category, SR 11-7 materiality, MDR event class, HIPAA breach category); timing of detection / reporting / mitigation; corrective action plan with due dates; residual-risk claim with evidence |

Note the overlap. Every audience wants the timeline, the cause, and the corrective action. The audiences diverge on framing (engineering asks for code, governance asks for register movement, regulator asks for obligation) and on the aggregation level (engineering wants the trace ID; governance wants the population impact; regulator wants the classification).

## The post-mortem shape

The document has ten sections, in this order, in one file, versioned in the incident-response repo. Extracts for each audience are generated by taking the sections the audience reads.

### 1. Header

- Incident ID; SEV; incident class (from chapter 01's taxonomy); systems affected; date range (detection → mitigation → post-mortem publication).
- Report status: draft / under-review / signed-off / regulator-filed.
- Signatories.
- Cross-links: harm-model row (mod-102), register row (mod-103), red-team fixture (chapter 04), regulator-package version (chapter 05).

### 2. Impact statement

- What harm actually occurred, phrased in the language of the harm model (mod-102 immediate → secondary → cascading → systemic). Named parties are counted where possible; population-scale estimates are given with confidence bands.
- Whether the harm has been remediated for affected parties (user notification, data recall, refund, medical follow-up as applicable).
- Regulatory classification: this is the field the regulator-facing extract lifts wholesale (chapter 05).

### 3. Timeline

A single unified timeline in UTC, one line per event, high enough resolution to reconstruct the response cadence. Rows include:

- First reproducible occurrence (from trace-store retrospective, if the true first is earlier than detection).
- First detection (monitor fire, user report, red-team result).
- Triage / class assignment / SEV declaration.
- Routing decisions (product IR / security IR / governance IR engagement).
- Mitigation actions with cutover timestamps.
- Reportability determination (chapter 05).
- Regulator notifications actually sent, with timestamps.
- Post-mortem draft, review, sign-off, publication.

The timeline is a *fact chain* — no analysis in it. Analysis lives in the next section.

### 4. Causal chain

The one-paragraph causal chain from chapter 02, step 6, expanded into a section. It names the deltas found, orders them by explanatory power, and cites the trace IDs / snapshot hashes for each delta. It also names the *contributing factors* that made the incident possible or hard to catch — e.g., the guardrail suite did not include the specific attack family, or the corpus-refresh path bypassed the review that would have caught the injected content.

Contributing factors are not causes; separating the two prevents the post-mortem from over-crediting any one delta with the entire outcome.

### 5. Evidence pack

Links (or hash-pinned locations) for every artifact the RCA depended on:

- Trace IDs (bad and paired-good traces).
- Model manifest before / after.
- Prompt / retriever / decoding config manifest before / after.
- Guardrail-effectiveness report versions.
- Drift dashboard snapshots.
- Supplier / dataset change record.
- SOC-side hand-off record (chapter 02).

This section is what makes the post-mortem re-runnable and what a regulator uses to spot-check any claim.

### 6. Risk-model reconciliation

- Does the incident match a predicted harm-model row (mod-102)? If yes, cite the row ID. If no, name the row that has been added to the harm model as part of the post-mortem — the *addition* is a required post-mortem action for unmodelled scenarios.
- Does the incident match a scored register row (mod-103)? If yes, cite the row ID.
- Residual-risk claim after the incident and the corrective actions — was the residual under-scored, correctly scored, or over-scored? What is the updated residual? The register row moves in response, with sign-off recorded.

### 7. Corrective action plan (CAP)

Every action has: owner (role and named person), due date, evidence of completion (what artifact will exist when this is done), and audit trail (where the evidence will live). A working table shape:

| Action ID | Description | Owner (role / person) | Due date | Evidence-of-completion artifact | Register-row credit |
|---|---|---|---|---|---|
| CAP-1 | Add indirect-prompt-injection attack family targeting KB-refresh path to the red-team suite (mod-104) and to the app-eval suite | Risk engineer (L25) / <name> | 2026-08-28 | Suite manifest v3.2 with new attack family; run report | HR-CS-INJ-01 residual reduction |
| CAP-2 | Add corpus-refresh pre-ingest scan for injection strings; block ingest on hit | Platform eng lead / <name> | 2026-08-21 | Ingest-pipeline config; monitor showing ingest blocks | HR-CS-INJ-01 residual reduction |
| CAP-3 | Add retrieval-distribution drift alert on novel-n-gram fraction; alert threshold 15% | SRE / <name> | 2026-08-14 (already shipped as containment) | Monitor config; alerting-runbook entry | HR-CS-INJ-01 residual reduction |
| CAP-4 | Add regression fixture to app-eval suite from the exploit's replayed trace (chapter 04) | Risk engineer + eval engineer (L35) / <names> | 2026-08-21 | Fixture file; suite run showing the fixture is green post-mitigation | HR-CS-INJ-01 residual reduction |

CAP owners have to be individuals, not "the team." A role without a named individual is a CAP the audit reads as unowned.

CAPs have review cadence: weekly during the treatment window (mod-103 chapter 06 residual-above-appetite cadence), then closed on evidence-of-completion sign-off. The governance-council packet (mod-112) rolls up open CAPs by age and by system.

### 8. Regulator classification and reporting log

- Which regulatory classifications apply? EU AI Act Article 73 serious-incident (which sub-category); SR 11-7 material MRM incident; FDA MDR event class; HIPAA breach; sector-specific reporting.
- What was reported, to whom, and when. Timing envelopes are cited (chapter 05).
- Which future reports are due, and when (updates, closure reports, annual summaries).

If the incident is *not* reportable, this section says so and cites the criteria that were checked. "Not reportable" is a documented decision, not an omission.

### 9. Learning propagation

- What was fed back into the harm model (mod-102)? A new row, an updated field on an existing row, or "no change" with a justification.
- What was fed back into the risk register (mod-103)? Residual move, credited-controls change, new row, or "no change" with a justification.
- What was fed back into the red-team / app-eval suites (chapter 04)? Fixture ID(s) added.
- What was fed back into the monitoring stack (mod-109)? New signal, threshold change, alerting-runbook entry.
- What was communicated to the risk council (mod-112)? Meeting reference; packet version.

### 10. Signatures

Sign-off by: incident owner, product IR lead, security IR lead (if engaged), governance IR lead, system owner, risk-engineer (this role), and the audience-specific sign-off — governance council chair (for the governance extract) and regulator-liaison (for the regulator extract) once those extracts are published.

Signatures are dated. A "signed" post-mortem with no dated sign-offs is not signed.

## Audience-specific extracts

Each extract is a *view* over the post-mortem, not a separate document.

### Engineering extract

Sections 1, 3, 4, 5, 7. This is what lands in the engineering-team channel and drives the CAP work. The extract is checked into the incident-response repo alongside the full post-mortem.

### Governance-council extract (mod-112)

Sections 1, 2, 6, 7 (summary of CAPs with owners and dates), 8 (regulator status), 9. The council reads the harm-model reconciliation and the register-row movement; they do not read the trace-ID list.

### Regulator extract

Sections 1, 2, 3 (timeline of detection / reporting / mitigation), 6 (residual-risk claim), 7 (CAP), 8. Additional formatting per obligation is chapter 05's scope; here we ensure the underlying facts land in the single post-mortem file so the extract is a lift, not a re-authoring.

## The incident-into-register update

The link from post-mortem section 6 to the register (mod-103) is an incident-triggered event source (mod-103 chapter 06 lists it). The update:

- The register row referenced in section 6 is edited to reflect the observed likelihood and severity — an incident is a data point, so the anchoring evidence updates.
- The credited-controls list is edited to reflect any control that was defeated by the incident (control is dropped or marked "defeated pending re-evaluation") and any new control that came out of the CAP (control credit added on delivery, not on plan).
- The residual score recomputes; if it moves above appetite, the row's cadence tightens (mod-103 chapter 06 table).
- Sign-off is triggered — row author + system owner + incident-response owner as signatories.

If the incident did not match a scored register row, the post-mortem adds one, with the incident as the anchoring evidence.

## The corrective-action-plan owner and cadence

The CAP is not a wish list. Two operational disciplines:

- **Owner accountability.** Every CAP has a role AND a named person, a due date, and an evidence-of-completion artifact. A CAP marked "in progress" for two review cycles without evidence movement is an escalation to the governance council.
- **Cadence.** Weekly stand-up during the treatment window; the incident owner runs the stand-up. On evidence-of-completion, the CAP is closed with sign-off and the register row is credited. Aged CAPs (past due date without evidence) surface in the mod-112 council packet.

Closing a CAP without evidence is an audit finding as serious as skipping the CAP entirely.

## The anti-pattern of a post-mortem only engineering can read

Symptoms and fixes:

| Symptom | Fix |
|---|---|
| No impact statement; document opens with a stack trace | Section 2 is mandatory; the harm-model language is used, not the log language |
| Timeline is Git commit messages | Timeline is a fact chain in UTC, one line per event, no analysis interleaved |
| CAP is "we will improve the guardrail" | CAP items have IDs, owners, due dates, and named evidence-of-completion artifacts |
| Regulator section is missing | Section 8 is mandatory; "not reportable" is written explicitly with criteria |
| No register-row link | Section 6 is mandatory; the register row is cited and the update filed |
| No sign-offs | Section 10 is mandatory; dated sign-offs make the post-mortem a controlled artifact |

The template exists to prevent these symptoms one-by-one. Do not remove a section on the grounds that "this incident didn't need it" — an empty section with a two-line justification is defensible; a missing section is not.

## Summary

- One post-mortem file, ten sections, three audience-specific extracts. Do not author separate documents per audience — the audit reads the disagreement.
- The three audiences (engineering, governance council, regulator) diverge on framing and aggregation, not on the underlying facts. Design the document to carry all three loads.
- The causal chain (chapter 02, step 6) becomes section 4; the evidence pack (section 5) is what makes the post-mortem re-runnable.
- The corrective-action-plan has IDs, named owners, due dates, and evidence-of-completion artifacts; CAPs without those are audit findings.
- The post-mortem drives an incident-triggered register update (mod-103 chapter 06) with residual-risk movement and re-signed row content.
